# Learning Module Builder

You are building a single `.html` file that behaves like a small course. The learner is typically smart but new to the domain, and their real goal is usually **confidence in an upcoming conversation** — with a systems engineer, a reviewer, a stakeholder. Optimize for "can they explain it in their own words afterward," not for topic coverage.

## The five commitments

Everything else in this skill serves these:

1. **Plain language first.** Every technical term gets an immediate translation — a hover tooltip on the term, or an "in plain words" callout box. Untranslated jargon is the exact place learners silently give up; one unexplained acronym can cost the whole section.
2. **Grounded in their reality.** If a PR, repo, or document is provided, every claim about it must come from actually reading it. Quote real code with a "real code from your PR" badge and a plain-words caption. Real snippets convert abstractions into "oh — that's *my* file." Never invent facts about the user's system: an invented "fact" the learner repeats to an expert destroys the exact credibility this module exists to build.
3. **Interaction is retention.** Quizzes after every section (retry until correct, explanation revealed on success), animations that make invisible processes visible (pipelines, timelines), and predict-then-reveal scenario games. A learner who commits to a prediction before seeing the answer remembers the answer.
4. **One page at a time.** A roadmap home page (the TOC), each section on its own page, progress stamps as sections are passed. A long scroll overwhelms; a stamped checkpoint motivates.
5. **A theme chosen by conceptual fit — fresh every time.** The central metaphor is picked by matching the topic's *mechanics* to a familiar real-world system that shares them (deployment traffic-shifting → highway lane management; caching → the pantry vs. the warehouse run), so the metaphor lets the learner predict behavior, not just enjoy the wallpaper. Follow the selection procedure in `references/theming.md` — write the topic's core verbs, score candidate worlds, stress-test with the hardest concept, and name where the metaphor breaks. Do **not** default to a favorite theme or reuse one from a prior module; if a repo/product name gifts a theme, accept it only when it survives the same scoring. And the metaphor never buries the real term: introduce both in the same breath, quiz on the terminology. The world it hands you supplies the palette *and* the per-category sigils — and the palette has to clear the colour-blindness gate before anything gets drawn (`references/palette.md`).

## How people actually learn (apply these deliberately)

The learner is a working professional: time-constrained, problem-centered, arriving with uneven prior knowledge, and likely to scan and jump rather than read linearly. Eight evidence-based techniques shape how the components get used — they're the difference between a module that informs and one that changes what someone can do:

- **Retrieval over re-reading.** Recall strengthens memory; re-reading doesn't. This is why quizzes follow every section — and why demos should ask for a **prediction before the reveal** ("before you press Run: which span will be longest?"). A learner who commits to a guess remembers the answer.
- **Pretesting — guess before you learn.** A failed guess primes the memory for its correction: prequestions reliably boost retention of the *specifically pretested* material (not the surrounding material — so aim them at the facts that matter most). This is why the roadmap carries 2–3 ungraded warm-up guesses the final quiz re-asks (blueprint §4), and why the core-mental-model section can open with a naive-design beat — "how would you build this with what you already know?" — commit first, then teach against where the naive design breaks (problem-solving before instruction, consolidated afterward, is its own replicated effect).
- **Interleaving confusable pairs.** Every domain has terms learners mix up (staleTime/gcTime, CSP/CORS, logs/traces, authn/authz). Find the module's confusable pairs, teach them **side by side** (a contrast table or twin cards), and quiz on *telling them apart* — discrimination practice beats teaching each in isolation.
- **Variation.** One example teaches the example; two or three varied examples teach the principle. For each core concept, vary the surface (different endpoint, different failure, different data) so the learner abstracts the pattern.
- **Elaboration.** Don't just show what something does — say *why it was designed that way*, *when to reach for it*, and *what the alternative was*. This is what the conversation-prep Q&As and code-peek "why" captions are for.
- **Reflection.** After a dense section or demo, a two-line "what we just did and why it worked" recap consolidates before the quiz. End the module with one open prompt: "how would you apply this to your own project?"
- **Spacing.** Revisit foundational ideas in later sections with light reminders and cross-links (plain `#section` anchors — the router makes this free), not full re-explanations. The per-section tooltip rule is spacing in disguise; lean into it.
- **Memory hooks for arbitrary facts.** Understanding derives most knowledge — but every module carries a residue of facts that can only be memorized: value tables, ordered stage lists, thresholds, defaults. For the 1–2 most critical such clusters, build a **visual mnemonic that encodes the structure** — the model is the trig hand trick, where finger position *n* physically maps to √n̅/2, so the image is a lookup device the learner can re-run, not decoration. Design rules and mechanics live in the blueprint's memory-hook section (§21): the hook must pass the derivation test, and you never quiz the mnemonic itself — mnemonic fluency masquerades as understanding, so the quiz asks for the *applied* fact.

Four supporting rules from the same research: **name misconceptions directly** (quiz distractors and prose callouts should say "people assume X — actually Y"; naming the wrong model is what dislodges it); **visuals follow the craft rules** — *carry* (a diagram must show what prose can't; one that repeats the paragraph is decoration), *contiguity* (labels live on the visual at the point of relevance, never in a distant legend), *signaling* (demos highlight the active element and dim the rest), and *coherence* (decoration never sits beside a teaching visual) — see the blueprint's visual craft rules (§20); **the module speaks conversational second person** — "you", "your request", "let's trace it" — conversational style beats formal register with one of the largest effect sizes in the multimedia literature; write like a sharp colleague at a whiteboard, never like documentation; and **terminology is frozen** — pick one name per concept and never swap synonyms for variety; every synonym is a new thing to reconcile. Finally, the cut test: if a section doesn't earn its cognitive cost, cut it or redesign it.

## Workflow

### Phase 0 — Understand the assignment

**When direction is unclear, ask — don't guess.** A learning module is a big investment of the learner's time; building the wrong one wastes an hour of theirs and all of yours. Use AskUserQuestion whenever the request leaves real forks open: What should the module **focus** on (a broad topic like "caching" hides five possible courses)? Are there **particulars to highlight** — a specific incident, a code area, a decision they need to defend? Who is the **audience**, and what conversation or decision is this preparing them for? How much **source-code depth**, and any interactive-element preferences?

**Set `multiSelect: true` on scope and stack questions.** "Which areas should this cover?" and "which parts of the stack?" are routinely non-exclusive, and a user answering "1 and 2" to a single-select question means the *question* was wrong, not the answer — you then have to guess which half they meant or spend another round. Audience and depth are usually genuinely single-select; scope and stack are usually not.

While asking, gauge **prior experience** — it changes the scaffolding, not just the content: full-novice scaffolding (worked examples, recognition quizzes, step-by-step hand-holding) measurably *backfires* on learners with real prior knowledge (the expertise reversal effect). An experienced learner gets a module that starts further down the guidance fade (blueprint §5), not a padded novice course.

Skip anything the request already specifies — don't re-ask. And if a genuine fork appears **mid-build** (e.g., the diff turns out to span three subsystems and going deep on all of them would triple the module), surface the choice to the user rather than silently picking. If running non-interactively (no user available), choose sensible defaults and say which you chose in the delivery note.

While clarifying the audience, read `references/personas.md`: two backstage archetypes — the skeptical senior engineer and the outcome-focused executive — that calibrate the module's arguments, Q&A registers, and sound-bites to whoever the learner's real conversation is with. They are never named in the module itself.

### Phase 1 — Gather facts before any HTML

- **PR provided:** don't flail — work down this ladder and stop at the first rung that works:
  1. **`gh` CLI first.** The user's own machine almost always has it authenticated. Try `gh pr view <n> --repo <org>/<repo> --json title,body,files,additions,deletions,author,state`, then `gh pr diff <n> --repo <org>/<repo>` (write to a file; strip lockfiles before reading). Important: run it **where the user's credentials live** — if your default shell is a sandbox, it likely has no `gh`/auth, so use the tool that executes on the user's actual machine (e.g., a desktop-commander/host shell) before concluding gh is unavailable.
  2. **GitHub MCP tools**, if a GitHub connector is present (search your available tools before declaring it absent).
  3. **Plain web fetch** of the PR page / `.diff` URL — works only for public repos.
  4. **Ask whether the code is local.** If gh and the connectors are all unavailable, don't give up on grounding — prompt the user (AskUserQuestion): "Is this repo cloned on your machine? Point me at the directory." A local clone is a *better* source than the PR API anyway: derive the diff with git (`git diff main...<branch>`, or `git log`/`git show` for the branch's commits), and you're already positioned for the read-around-the-diff step below.
  5. **Last resort: ask the user** to paste the diff or run `gh pr diff <n> > pr.diff` themselves and attach it.

  Read the *whole* diff. The PR description's test plan and notes are gold — they contain the author's honest open items and caveats; carry those into the module (they make the learner credible).
- **Read around the diff, not just the diff.** A diff shows what changed, never what it changed *into* — and modules built from the diff alone explain code out of context. Pull up the surrounding codebase for: the **interfaces/types the new code implements** (the diff shows a class; the base interface lives elsewhere), the **callers and entry points** that touch the changed code, the **pre-existing system it plugs into** (what did the logger/router/pipeline already do before this PR extended it?), related **config and tests**, and any **docs/ADR/plan files the PR description references**. This context is what makes the seam explanations, the annotated walkthrough, and especially the adversarial review correct — half the real review findings (other write paths not invalidated, conventions the PR breaks or follows) are invisible in the diff itself. How: the repo is usually cloned on the user's machine — find it or ask where it lives and read files directly; or fetch individual files via `gh api`/a shallow clone. Scope discipline applies: read what the module needs to explain correctly, not the whole repo.
- **Repo / files / links provided:** read or fetch them.
- **No source provided:** judge topic freshness. Fast-moving or niche → WebSearch first; stable fundamentals (SQL indexes, HTTP, caching theory) → trained knowledge is fine.
- **Budget the research; don't fan out.** Four heavy research subagents launched in parallel will hit a session limit and most of them return nothing — a whole round lost with nothing to show. What works: **one well-scoped deep subagent on the densest area, plus targeted direct searches** for everything else. And **write the fact sheet incrementally** as findings land, so a killed agent costs one topic rather than the round.
- **For domains that turn over in months, teach the procedure, not the leaderboard.** Sort what you found into **durable** (mechanisms, economic shapes, failure modes, tradeoff structures — these age in years) and **perishable** (model names, version numbers, prices, benchmark scores, rankings — these age in weeks). Build the module from the durable half, deliberately omit the perishable half, and teach the **selection procedure** instead: "how to choose a model for a step" outlives "which model is best today." Then **say so inside the module**, in a visible callout on the relevant page — naming the staleness converts a liability into a teaching moment, and a learner who can re-run the choice beats one who memorised this quarter's winner.
- **When sources conflict, do not average them.** Prefer primary sources (official docs, the vendor's own changelog, the paper itself) over aggregators, and label aggregators as aggregators when you cite them — SEO-farmed roundups routinely disagree with each other on versions and benchmark numbers. If a conflict can't be resolved against a primary source, either **omit the claim** or **state the disagreement** ("sources differ — X reports A, Y reports B"). Never split the difference into a confident-sounding number that no source actually supports; a fabricated midpoint is the one error the learner will be caught repeating.
- Build a **fact sheet** as you go: exact file names, function/symbol names, env vars, endpoints, defaults, intervals, thresholds, versions, open items. The module will be fact-checked against this sheet in Phase 4.
- Record **every source you consult** (URL + one-line takeaway) in the fact sheet. These become the module's further-reading page — learners consistently want to keep going after the course, and handing them the actual documentation you used is the honest version of "further reading." Never pad this list with links you didn't open or can't vouch for.
- **Read the source critically, not at face value.** A learning module that presents flawed code as gospel teaches the flaw. While reading, log two lists in the fact sheet: *issues* (anything against best practice or likely to bite — with why it's a problem and what the correct pattern looks like) and *strengths* (deliberate good decisions — with why they're good). Both get taught: issues inline where the concept comes up ("by the way, this line has X problem — here's the standard fix") and again in the closing adversarial review section.
- Choose the **central metaphor** via `references/theming.md` (mechanics-first selection, scored candidates, stress-tested, breakdown named) and 2–4 color-coded categories — one accent per concept type, used consistently in every diagram, card, and demo, each paired with a **sigil**: a hue-independent shape that identifies the category with the colour removed (blueprint §24).
- **Gate the palette here, not at the end.** Whether a colour-blind reader can separate your accents is not intuition-checkable — a palette hand-designed to be accessible produced two "obviously different" warm tones a deuteranope reads as ΔE00 2.3 apart. `scripts/verify-module.mjs --palette` scores candidate accents in one command before any CSS exists (`references/palette.md`); separate categories by **lightness** and let hue decorate on top, because simulation collapses the hue circle toward a blue↔yellow axis. A collision found here costs one edit; found in Phase 4 it costs a repaint of every diagram, chip and chart in the file.

### Phase 2 — Architect the course

Read `references/module-blueprint.md` for the component inventory and code patterns. Then plan sections along this arc, merging or dropping steps for smaller topics:

1. Why this exists — the pain without it, told as a concrete day-in-the-life scenario
2. The core mental model(s) — the 2–4 concepts everything else hangs on (strong opening beat: pose the naive design first — "how would you build this with what you already know?" — let the learner commit, then teach against where the naive design breaks)
3. Deep-dive the scariest term — the word that made them ask for help
4. The standard / ecosystem — where this fits in the wider world
5. End-to-end journey — one animated walk through the whole pipeline/lifecycle
6. Their source, mapped — every file/change in one sentence, plus an **annotated line-by-line walkthrough** of the 1–3 files that carry the lesson (source-grounded modules)
7. Obstacles and gotchas — the honest "what can go wrong / what's still open"
8. The tooling they'll touch — what they'll actually click and look at
9. **The Big Picture** — one page in two halves (blueprint §15): the central diagram with terms, numbers, and takeaways pinned onto it, *and* the reference half — the symptom→cause→fix table, every number with its lever, decision rules, a code skeleton, a persisted checklist, anti-patterns, and the vocabulary spine. Modules are learned once and referenced forever; the second half is the one that's usually missing
10. **Adversarial review** (source-grounded modules) — a balanced critique of the PR/source: the issues (what, why it matters, the correct pattern) and the strengths (what, why it's good), framed as training the learner to run this review themselves
11. Conversation prep — likely expert questions with strong answers ending in a **sound-bite they can say verbatim**, tuned per `references/personas.md` (engineering-reasoning answers for the skeptical senior engineer; outcome-language sound-bites for the executive) and finished with the two-lens check it describes
12. **Glossary** — the flip-card deck as its own page (not buried inside another section; learners return to it)
13. Final assessment — a cumulative quiz with a completion stamp, followed by **further reading** (the annotated sources list from Phase 1)

Default sizing for a "zero to hero" request: 8–12 sections, ≥15 quiz items across sections, ≥20 glossary terms, and **8–15 interactive or visual elements, at least 3 of which are charts or simulators the learner drives with a control** (blueprint §22). That lands at roughly **3,500–5,000 lines** of HTML. A 2,000-line "zero to hero" module is under-built, and the shortfall is always the same one: sparse visuals. Topics that look purely conceptual are usually dense with numeric relationships nobody bothered to plot — reliability compounding, cost scaling, growth curves, capacity budgets. Find them in Phase 1 and plan the charts before writing prose, because charts retrofitted in a second round should have been in the first. For a "quick explainer" request: 4–5 sections and 3–5 visual elements (fold Big Picture, glossary, and sources into fewer pages rather than dropping them). Every teaching section ends with 1–4 quiz items — that's what stamps progress.

**The non-negotiables.** However the arc gets merged or themed, a full module always ships with: the visual roadmap landing page, **a hero animation that runs the module's thesis** (blueprint §1 — the central process executing end to end on a loop, not atmospheric drift; the test is that a stranger who watches one loop and reads nothing can say what the system does), **charts and parameter explorers** (blueprint §22 — at least three learner-driven ones in a full module), **at least one animated process demo** (stepper, timeline, or simulator — the subject matter is dynamic, watching it run shows what prose can't, and this is consistently the most-praised element; note this is a property of the *content*, not of "visual learners" — modality-matched "learning styles" are a debunked myth, so never design or explain the module in those terms), per-section quizzes, **inline term tooltips throughout every section** (since pages are viewed in isolation, each technical term self-explains on first use per section — learners call this their orientation system), a glossary page of its own, the Big Picture page **with both halves — mental model and reference** (blueprint §15, the symptom→cause→fix table included), a further-reading/sources page, a **`prefers-reduced-motion` fallback** for the hero and every demo, **a gate-passing category palette with a sigil per category** (blueprint §24 — colour never identifies a category on its own), and — when a PR/repo/doc was provided — the annotated code walkthrough **and the adversarial review section**. Treat these as the definition of "done," not as options.

One quality bar on the animated demo: **animate the subject, not the scaffolding.** The demo must show the domain's actual moving parts — requests as dots flowing to cache vs. database, traffic shifting between blue and green, a span tree growing under a click — because "watching the cycle happen" is what no static description can deliver. A generic stepper advancing through labeled boxes is navigation, not visualization; if the module's only animation is a stepper, add a real simulator of the core process. And every demo obeys the visual craft rules (blueprint §20), which are stated once there and not repeated here: pretrain every moving part before the demo, signal the active element, advance in learner-paced beats, stay replayable.

### Phase 3 — Build

Single self-contained file, vanilla JS only (no frameworks, no CDN scripts — the file must work as a local double-click artifact). Google Fonts with system fallbacks so it degrades offline. Three-font system (display / body / mono), CSS variables for the whole palette — category accents named `--cat-<key>` after the concept, never the colour — and a committed aesthetic, never generic defaults. Define the sigil set alongside the accents so every later component gets its second channel for free (blueprint §24).

Build in chunks: `Write` the skeleton + full CSS first, then `Edit`-append sections a few at a time, then `Edit`-append the script. A 4,000-line file written in one shot invites truncation errors; chunks keep each step verifiable. Build the chart helper (§22a) early, in the first script chunk — every later chart is then one call, which is what makes the visual floor cheap instead of a second round of work.

Use the component menu from the blueprint: roadmap cards with stamps, hash router, quiz engine, term tooltips, code peeks with plain-words captions, annotated line-by-line walkthrough, pipeline stepper, timeline/waterfall demo, scenario-prediction game, **slider-driven line charts from one shared helper, relative-unit cost calculators, matrix/heatmaps, before/after state toggles** (§22), memory-hook panel, the two-half Big Picture with its symptom→cause→fix table (§15), flip-card glossary page, accordion Q&A, sources/further-reading list, final quiz with certificate stamp, guarded progress persistence, and **Markdown/HTML exports plus a print stylesheet** (§23).

**Author repeated content as data arrays before you render it** (§23). Anything appearing in a section *and* the Big Picture *and* an export must have exactly one definition in the file — otherwise you buy a drift-guard test where a shared array would have cost nothing.

Content principles while writing:

- **Numbers stick.** Thresholds, defaults, intervals — always paired with *what moves them*. When a cluster of such numbers must be memorized rather than derived, give it a memory hook (blueprint §21).
- **Honest limitations are a feature.** "This part is still blocked on X" and "this doesn't scan free-text messages" are what make the learner sound trustworthy in the real conversation.
- **Quiz wrong-answers should be plausible** — each distractor represents a real misconception, and the explanation names why it's wrong. Default to **three options** (one correct, two plausible distractors — decades of item-design research: a fourth is nearly always nonfunctional filler), and after a second wrong attempt, hint at the misconception without revealing the answer (blueprint §5).
- **The metaphor never replaces the term.** Say "a span — one timed stopwatch lap," not just "a lap."

### Phase 4 — Verify (not optional)

**Start with the bundled verifier**: `node scripts/verify-module.mjs <module.html>` **must exit 0**. It mechanically enforces the paged-navigation and progress-tracking contracts (reload survival and the no-clobber rule included), the reduced-motion fallback, the quote-nesting lint, the **colour-independence gate** (every `--cat-<key>` pair separable under deuteranopia, protanopia and tritanopia, each with its `.sigil`), and — for modules of 8+ sections — the visual floor and the reference half's `table.fixtable`. It resolves `jsdom` from **the directory you run it in**, so `npm i jsdom` in a scratch directory and run from there; verification.md §0 has the exact incantation and the copy-it-elsewhere fallback. Run it as-is: never replace it with a hand-rolled smoke test (hand-rolled tests are how these bugs shipped twice) and never edit it to make a failing module pass.

Then run the rest of `references/verification.md`: tag balance, extracted-JS syntax, referenced-ID cross-check, quiz answer-index bounds, the module-specific jsdom smoke test, and the content-integrity checks — **recompute every number the module prints** (a module that teaches compounding must not get its own compounding wrong), **assert every duplicated figure agrees across section, chart, and cheat sheet**, **sum every table that implies a total**, **assert behaviour, not rendering, on every interactive element**, and **export fidelity** where exports exist.

Then the **grounding audit**: every codebase claim traces to real code — script-diff the "real code" excerpts against the source, sweep every named identifier, run the sentence-level claims ledger — and **every chart declares whether it is measured or illustrative, and where its numbers came from**. A chart with neither real data nor an illustrative badge is a bug: a smooth authoritative curve drawn from invented numbers is a fabrication wearing a chart's clothes, and it is more persuasive than the bad sentence you would never have shipped. If you didn't read it, the module doesn't claim it. Fix and rerun until clean.

### Phase 5 — Deliver and iterate

**The delivery folder contains exactly one file: the .html module.** Whatever sits next to the deliverable is what the user opens first — a stray `smoke-test.js` or `vcheck.py` beside the module reads as "you delivered a JavaScript file." Run verification scripts from a temp directory, and before finishing, delete anything you wrote alongside the deliverable.

Save to the user-visible outputs folder (short filename), present the file, and summarize in 2–3 sentences — what it covers and the one or two most interesting things inside. Offer the obvious next iterations: more depth on any section, restructuring, new sections. When iterating on an existing module, keep the same localStorage key so the learner's progress survives the update.
